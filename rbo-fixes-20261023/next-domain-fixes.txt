Domain and scalar-demand fixes: source review and prepared implementation
Base: e8700d379b3b9c4fbaf68f36424e6bcf08314fd2
All four commits are independent children of this base. No build or native
execution was performed by this reviewer. No rendered inputs are retained.

C06 — exact capture types
Prepared: 446592a476b92437df5b2579e1027cfb313be1d9
TEliminateDependentJoinDomainRule previously copied an inner IU into a capture
without comparing its type with capture.Type. Consumers later build null-safe
domain keys with StablePickle, whose encoding is type-dependent.
The rule now requires current types and declines a binding unless the full
annotations match, including optionality. This deliberately does not insert a
potentially lossy cast. Unknown types also decline the shortcut.
Relevant source: dependent_join_pushdown.cpp, binding collection/rebinding;
kqp_rbo_type_ann.cpp ComputeTypes(TOpAddDependencies) uses capture.Type.

C07 — retain equality after binding
Prepared: 2e4843e6be7a7b49fab191bc0d454653e0aca41e
The same rule discarded selected equalities, retaining only Exists for optional
inputs. Present NaN values therefore passed where the original predicate did
not. Keep the original equality conjunct after constructing the binding Map;
its self-comparison still rejects nonreflexive values. This also preserves the
original NULL behavior and removes the weaker, redundant Exists substitute.
This is more precise than rejecting every floating-point correlation or
disabling domain elimination. Decimal/composite/PG equality controls remain
worth exercising; no yql/essentials changes are required.
Read-only cross-check: StablePickle canonicalizes floating-point negative zero
and NaN bits in mkql_computation_node_pack.cpp through fp_bits.h. This does not
make SQL equality reflexive for NaN; the retained predicate is still necessary.

Fallback support for declined domain elimination
The stage orders TPushDependentJoinThroughFilterRule after elimination. It moves
the original Filter above the dependent join. The resulting AddDependencies
pattern is accepted by TRewriteDependentJoinToCrossJoinRule, which substitutes
captures with the actual domain columns and creates Cross(domain, inner).
The stage restarts after each applied rule (kqp_rbo.cpp RunStage), so the
unsupported-dependent-join fallback is not the next operation on the old shape.
This preserves supported decorrelation for the specific guarded pattern.

C05 — scalar-origin domains stay restricted
Prepared: bf6527096b7a594beb47e3b2e274079b184b8128
Scalar cardinality aggregation is created above the dependent subquery in
inline_scalar_subplan.cpp. Removing its demanded domain lets unrelated inner
keys reach that validation. A PreserveDomain policy now marks scalar-origin
dependent joins; the elimination shortcut declines them. Normal pushdown and
cross-domain rewriting remain available. IN/EXISTS calls retain their previous
eligibility. Constructor, PushInto, PushIntoCopy, reduced-domain construction,
TSubplanDomain::Bind and CopyImpl carry the policy explicitly.
An ancestor scan for an Ensure node or generated IU name was rejected as a
fragile way to infer semantic purpose. Preserving the domain is conservative
for scalar optimization quality but restores the required evaluation set.

C15 — validate at the original expression use
Prepared: 3a9521680600ea2f5bcdb2ea0736e8d2cdb5df5d
MakeScalarState produces raw value/count state. CheckScalarAtUses substitutes
an Ensure at each original scalar Member in its expression, using that same
row argument. It leaves IF/COALESCE guards in place. A missing correlated right
row gives count zero and NULL value. A demanded multirow scalar still fails.
Fresh scalar call IDs are allocated per converted expression in
kqp_plan_conversion_utils.cpp; replacements target that call's row Members.
Moving the Ensure only into a Map above the join would still be eager and was
not used. Checking only one global demand flag would also be insufficient when
the same correlation domain is demanded by some outer rows and skipped by others.

Scope limit for C15
This fixes the verified scalar-cardinality hoist. It does not make arbitrary
error-producing expressions inside the subquery body lazy. A full conditional
subplan-execution design would need demand extraction through lazy constructs,
single evaluation of volatile guard expressions, requested-domain filtering,
and barriers against moving error-producing maps below that filter. Merely
cross-joining an empty demand relation cannot guarantee a separately scheduled
inner branch was never evaluated. Keep that wider behavior explicitly unverified.
